# 第三阶段 邮件解析与全量清洗

日期：2026 年 10 月 13 日。

已在固定的 400 封开发样本上调试解析器，随后完成全部 64,620 封邮件的主题/正文解析、清洗和质量核验。全部邮件保留了至少一项可用文本，其中 1,422 封仅保留主题。正文缓存只保存在本地；代码、人工机制示例和聚合统计随本阶段提交上传。

这里的“可用”仅表示清洗后有字母或数字字符，包括中文字符，不代表内容无乱码，也不代表已经适合独立测试。内容去重、正式划分和模型训练在后续阶段进行。

**复现步骤**

在已配置好外部语料目录、完成前两阶段的仓库根目录执行：

```powershell
.\.venv\Scripts\python.exe scripts\clean_mail.py --scope development
.\.venv\Scripts\python.exe scripts\check_cleaning.py --scope development
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe scripts\clean_mail.py --scope full
.\.venv\Scripts\python.exe scripts\check_cleaning.py --scope full
```

`clean_mail.py` 支持 `--config`；默认优先使用被忽略的 `config.local.json`，数据位置也可由 `TREC06C_ROOT` 覆盖。输出固定在项目 `artifacts` 下，原始语料须位于仓库外。

启动前核对索引 SHA256、canonical 清单、稳定路径 ID、标签及开发抽样结果。逐封读取后核对文件大小，并记录原始内容的聚合输入签名，以追踪实际读取的数据版本。相同大小的内容变更不能仅靠旧索引审计被发现；聚合签名用于后续版本比对，不是内容去重结果。

返回码：完整处理且无运行 `error` 为 0；逐封运行错误为 1，其余邮件继续处理并输出账目；配置/输入等致命错误为 2，旧产物可能仍存在。`summary.passed` 不保证所有邮件都有有效文本，必须同时看 `usable_records` 与隔离数量。

**处理规则**

1. 用二进制 MIME 解析保留原始字节，主题按 RFC 2047 编码词解码；只使用主题和选定正文，不把 From、To 或路由头加入模型文本。
2. 先处理 base64、quoted-printable 等传输编码，再尝试声明字符集。声明不适用时参考 BOM、HTML charset 与 UTF-8/GB18030/GBK 回退；记录实际使用编码、回退、替换符及质量警告。
3. base64 声明错误但 payload 已是明确可读文本时，有记录地保留原字节。未知编码、无法恢复的传输数据或明显二进制内容拒绝该候选，不妨碍其他正文或主题保留。
4. `multipart/alternative` 优先选择一个有效纯文本表示，失败再取 HTML；`related` 取根部件；一般多部分组合可用文本并去掉同一封内部的重复表示。附件及转发的整封子邮件跳过。这里的内部重复消除不代替第 4 步的跨邮件内容去重。
5. 声明 multipart 但实际无可拆分部件时，尝试文本回退。仍含实际声明边界或连续 MIME 内容头的候选拒绝；普通装饰破折号不作为损坏 MIME 的证据。
6. HTML 使用 Beautiful Soup 去除 script/style/head 等不可读内容，保留实体、段落与锚文本；不访问图片或链接。
7. 主题/正文统一进行 NFKC、英文小写、控制字符清理、空白归一化，并把常见 URL、邮箱、电话号码转换为 `urltoken`、`emailtoken`、`phonetoken`。普通数字保留。这些规则不构成全面匿名化。
8. 正文候选的替换符或控制字符比例超过 2% 时拒绝；短主题允许至多 2 个替换符，避免因单个坏字符丢弃大部分可读标题。private-use 字符仅标记，不能一概视作乱码删除。

**状态和统计口径**

`ok` 表示所考察文本未触发已记录的恢复/质量信号；`recovered` 表示有正文且发生回退、MIME 缺陷、替换符或其他质量信号；`subject_only` 表示只有主题可用。三者可供后续去重筛选。`empty`、`quarantined`、`error` 不进入可用数据。本次后面三种状态均为 0。

`recovered` 不是“语义完全修复”的保证；`subject_only` 优先于恢复状态，因此标题专用邮件也可能含恢复标记。异常日志包含所有非 `ok` 邮件，不能把该日志行数当成隔离数量。

`has_html` 只统计所选有效正文是否经 HTML 提取；`has_html_part_anywhere` 统计任一 MIME 部件的 HTML 声明。一个邮件可以命中多个编码、缺陷或恢复动作，相关计数不能相加当作总邮件数。

attempt 字符口径为每个被考察主题段/正文候选的一次解码结果，包含后来被拒的候选，不包含内部 codec 探测；retained 字符口径仅按最终 `text_clean` 计算。替换符按 U+FFFD 计数，不能据此完整识别所有语义乱码。

**开发验证与修正**

固定开发样本为 ham/spam 各 200 封。最终互斥状态为 `ok` 156、`recovered` 239、`subject_only` 5，隔离与运行错误为 0。

Luna 子代理独立复核了开发样本的 MIME 结构和 40 封问题优先样本的规则元数据；主代理另做了 8 封清洗文本的有限本地抽查。实际邮件摘录没有写入仓库，公开机制演示全部为人工构造。这些检查不代表对 64,620 封的逐封人工语义验收。

开发中发现并修正了以下问题，均有相应回归覆盖：装饰破折号误触发 MIME 拒绝、单个坏字符导致短主题被丢弃、带多空格电话号码造成清洗不幂等、转发部件跳过计数遗漏，以及未选 HTML 表示误计入有效正文 HTML 率。对原始语料存在的部分乱码仅保留质量标记，没有用标签或最终分类效果倒推清洗规则。

**最终检查证据**

- 完整测试集实际运行 42 项：41 项通过、0 失败、0 错误、1 项跳过。跳过的是第二阶段已有的符号链接测试，原因是本机 Windows 不允许创建符号链接；新增 33 项均执行通过。
- 开发和全量分别通过 13 项核验，包括解析源码指纹、所有 ID 可对账、输入/输出数量、标签、互斥状态、可用/隔离账目、输入与缓存 SHA256、attempt/retained 字符统计、无运行错误及逐行规则检查。
- 全量逐行归一化幂等、常见联系模式与控制字符规则检查没有发现违规；这只验证已实现模式，不保证所有身份信息被删除。
- 开发缓存、异常日志和聚合摘要重新运行后字节级一致；400 封开发结果与全量缓存内对应记录逐字段完全一致。审查补强源码来源记录后重跑全量，缓存与此前全量结果的 SHA256 相同。
- summary 记录生成时解析源码的 SHA256，validator 对照当前源码并核对每行 `parser_version`；首个发布版本为 `1.0`。人工测试确认修改源码后不能继续验收旧缓存。
- 公开 validator 只保留抽查数与状态分布等汇总，逐封 QA 名单与稳定 ID 留在本地忽略目录；人工测试检查这一边界。
- Git 忽略核验覆盖两种缓存、两种异常日志、两种 QA 名单、本地配置与虚拟环境；私有缓存目录中唯一被跟踪的文件为 `.gitkeep`。
