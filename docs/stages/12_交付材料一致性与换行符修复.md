# 阶段十二：交付材料一致性核对与换行符修复

完成日期：2026 年 10 月 26 日。承接第十一阶段的项目说明文档与演示 PPT，本阶段不改动任何模型、划分或指标，只修复两处会让读者被误导的问题：文档里已经过时的上传状态描述，以及工作区换行符漂移导致锁内指纹无法核验的问题。

## 目标与边界

- 把全仓库中「GitHub 写入被 403 阻塞、尚未上传成功、需从 bundle 恢复」这类已经过时的描述改成实际可核验的远程状态。
- 让 Windows 检出后的工作区字节与提交内容一致，使 `final_lock.json` 引用的指纹在本地可直接核验。
- 为说明文档与演示 PPT 增加数字一致性校验，防止文档与实验结果脱节。

本阶段不修改实验代码、不重跑模型、不改动 `artifacts/` 中任何锁内证据。

## 实际发现的问题

**1. 文档描述与远程状态不符。** 仓库所有者已将组员账号加入协作者，写入权限恢复，续作分支实际已推送并在远程核验，但 README、执行清单、项目报告正文、文件用途索引、答辩提纲和六个阶段记录仍写着 403 阻塞。其中 `deliverables/项目报告.docx` 是直接交给老师看的文件，正文里写着「当前 GitHub 应用写入返回 403，续作尚未上传成功」，属于内容不实。

**2. 换行符漂移使锁内指纹失效。** `core.autocrlf=true` 时，Markdown 与 JSON 的工作区副本被写成 CRLF，而提交内容仍是 LF。提交版本本身与锁一致，但工作区副本的 SHA256 与 `final_lock.json` 记录值不符：

```
artifacts/audit/cleaning_summary.json
  提交内容  3,635 字节  SHA256 5a3796c3…16cf21   ← 与锁一致
  工作区    3,756 字节  SHA256 8d9ea77e…4ff92d   ← 与锁不符
```

该文件被 `final_lock.json` 引用，所以这不是外观问题：一份新克隆若在 Windows 检出，同样会对不上锁内指纹。

## 一致性校验脚本

新增 `scripts/check_guide_consistency.py`：从公开聚合产物重新推导 28 项关键数字，逐一确认它们仍出现在说明文档与演示稿中。

演示稿按**构建后的 .pptx** 校验而不是按生成器源码校验，因为读者看到的是成品。脚本读取全部文本框与表格单元格。

两项数字不要求出现在演示稿中：去重移除数量（演示稿给出的是连通分组数 30,817，语义更贴切）与 ham 类 F1（演示稿用 TN/FP/FN/TP 四格替代）。该豁免在脚本中显式声明并被测试覆盖。
