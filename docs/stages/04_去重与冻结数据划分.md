日期：2026 年 10 月 14 日。

已对第三阶段的 64,620 封可用邮件审计精确重复，去掉 30,632 份同标签、相同最终文本的副本，保留 33,988 封代表，未发现精确内容标签冲突。训练/验证/测试集固定为 23,792 / 5,099 / 5,097 封。全部内容关联分组保持在同一个集合，开发样本接触过的整组只进入训练侧。

在已完成前三阶段、配置外部数据位置的仓库根目录执行：

```powershell
.\.venv\Scripts\python.exe scripts\split_data.py
.\.venv\Scripts\python.exe scripts\check_splits.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

`split_data.py` 可通过 `--config` 选择配置，数据路径也支持 `TREC06C_ROOT`。本版本冻结契约为种子 42 和 70%/15%/15%，配置必须相符。生成前核对源索引、清单、开发样本、清洗缓存、解析源码及行版本；逐封重读原始文件，校验路径、大小及完整字节聚合签名，与第三阶段输入保持一致。

生成器在写入前调用独立 validator 检查候选结果；失败不发布候选。重复运行不得覆盖不同的已冻结清单或来源记录，返回 2 并保留旧版，不能通过试不同种子挑好看的模型成绩。同版缺失的本地账本可以在公开冻结产物一致时重建。成功退出 0；独立检查不通过为 1，配置/输入等致命错误为 2，旧记录可能仍存在。

**去重、冲突与分组是三件事**

1. 原始字节签名：SHA256(完整原始邮件文件)，包含邮件头，只用于原始精确重复审计和分组。本次每个源文件字节签名不同，并不说明正文不同。
2. 最终文本签名：对缓存 `text_clean` 原字符串精确计算签名，不另行删除标点或空白。这是主模型的主题＋正文输入，同标签同签名仅保留一个代表。
3. 有效正文签名：仅当 `body_empty=False` 且正文含字母/数字字符时，对 `body_clean` 精确签名。相同正文而标题不同的邮件不直接删除，但须同组分配。5 封非空但只有符号的正文不建边，避免装饰字符合并无关邮件。
4. 对照输入签名：对 `text_unstripped_html` 精确签名，保证第七阶段 HTML 对照也不会通过相同输入跨集合。

文本签名格式为 SHA256(UTF-8(`trec06c-content-v1` + NUL + 字段名 + NUL + 文本))。各字段有独立命名空间，只比较同字段相等关系。路径 `mail_id` 仍是路径标识，不能代替内容签名。

共享上述任一字段键的邮件连边，取传递闭包形成关联组。相同原始字节或相同最终模型文本却跨标签的**精确键整组**隔离，不多数投票；不会自动删除仅通过不同正文/对照表示间接连通的所有其他邮件。共享正文、标题不同且标签不同，可以是有意义的不同输入，只同组分配并统计。本次所有这些跨标签情况均为 0。

同标签最终文本重复组优先保留开发样本成员，再按 `mail_id` 字典序取最小者；不以模型效果或人工偏好挑代表。重复记录仍保留到本地账本，映射到代表及其所属集合。第七阶段同样使用这批固定代表，不能重新为对照方案去重挑样本。

**去重账目与类别变化**

| 处置 | ham | spam | 合计 |
|---|---:|---:|---:|
| 原始可用输入 | 21,766 | 42,854 | 64,620 |
| 保留代表 | 21,411 | 12,577 | 33,988 |
| 同标签最终文本副本 | 355 | 30,277 | 30,632 |
| 精确标签冲突隔离 | 0 | 0 | 0 |
| 不可用隔离 | 0 | 0 | 0 |
| 类内代表保留率 | 98.37% | 29.35% | 52.60% |

对账：33,988 + 30,632 + 0 + 0 = 64,620。垃圾邮件原本重复更多，所以去重后 spam 占比由 **66.32% 降为 37.00%**，多数类变为 ham。后续多数类基线必须由训练集重新确定，不能把原始 66.32% 当作去重数据的基线。

这是去重规则造成的样本权重改变，不是丢弃难样本或模型改进。后续指标描述的是历史语料中不同规范化文本的分类能力，不能直接当作真实邮箱自然来信频率下的效果。

**开发样本与划分规则**

先在所有原始记录上建关联组，再隔离精确冲突和选代表。因此即使某封开发邮件最后被去重或隔离，它已暴露的正文/对照关系仍会约束整个组件，不会重新流入验证或测试。

400 封开发邮件中，384 封为保留代表，16 封归入重复映射。它们触及 **372 个关联组、1,738 封保留代表**，全部固定到训练侧。去重前关联组共 30,817 个、最大 1,409 条原始记录；去重后仍为 30,817 组、最大 432 个不同最终文本代表，混合标签组为 0。

按两类保留代表数分别计算最大余数整数目标。先分配开发接触组到 train，其余组按代表数从大到小处理；同大小组用种子＋稳定组 ID 的 SHA256 排序。每组选择使三集合类别数量目标的归一化平方误差增量最小的集合；平局也用种子固定。整个组不能拆开，因此算法一般只保证近似分层。本次两类整数目标均恰好命中。

| 集合 | ham | spam | 总数 | 代表占比 | 关联组数 |
|---|---:|---:|---:|---:|---:|
| train | 14,988 | 8,804 | 23,792 | 70.0012% | 21,609 |
| validation | 3,212 | 1,887 | 5,099 | 15.0024% | 4,604 |
| test | 3,211 | 1,886 | 5,097 | 14.9965% | 4,604 |
| 合计 | 21,411 | 12,577 | 33,988 | 100% | 30,817 |

总比例相对 70%/15%/15% 的偏差分别约 +0.0012、+0.0024、−0.0035 个百分点，来自按类别取整数后的求和。三套集合的 spam 占比均约为 37.00%。

**实际验收与边界**

- 完整测试集共 70 项：69 项通过、0 失败、0 错误、1 项跳过。跳过项仍是旧索引测试的 Windows 符号链接权限限制；本阶段新增 28 项全部执行通过。
- 独立 validator 的 24 项检查全部通过，重建了 30,817 个关联组，核对原始/最终文本/有效正文/对照输入没有跨集合相同键，代表 ID 唯一、开发关联组只在训练侧、逐封处置和各类账目完整、所有来源和固定产物指纹相符。
- 原始哈希由生成器逐封重读真实文件；validator 无须再次打开原邮件，而是按 canonical 清单顺序重算账本原始哈希的聚合签名，与第三阶段真实读取签名比对。正文及掩码前表面签名由 validator 从缓存重新计算。
- Luna 在不读取正文的前提下，独立从账本签名重建分组与公开 CSV，确认同一分区、重复映射、全部样本和类别计数一致，跨组/开发边界违规为 0。
- 真实语料将缓存行顺序和代表顺序逆序重放，去重摘要、三套 CSV 和私有账本与原结果字节级一致。该复现检查使用已校验的本地原始/掩码前签名，没有声称第二次全量读取原始邮件。
- 合成负向测试覆盖篡改标签/原始哈希/公开统计、缺失 checksum 条目、错误正文空标记、重复副本跨集合、源码变化和不同 seed 覆盖冻结。即使重算局部 checksum，结构或来源不一致仍会被拒收。
- 公开文件没有真实主题/正文、内容签名、关联组标识或文件路径；完整账本及测试临时记录受忽略规则保护。新冻结元数据的 LF 换行规则保证 Windows Git 检出后不改变字节指纹。

详细证据：[去重与划分统计](../../artifacts/audit/split_summary.json)、[独立验证](../../artifacts/audit/split_validation.json)、[Luna 聚合复核](../../artifacts/audit/stage04_independent_audit.json)、[逆序复现](../../artifacts/audit/stage04_reproducibility.json)、[阶段验证](../../artifacts/audit/stage04_validation.json)。

精确一致性检查不能识别所有近重复广告模板，也不能消除历史语料的语义乱码、短主题信息不足和真实流量分布差异。这里未使用分类效果制定规则，也未拟合词表、IDF 或模型。
