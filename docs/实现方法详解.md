本文回答一个问题：**这套流程每一步到底是怎么实现的，为什么这么做。** 结论与指标已在 [项目说明文档](项目说明文档.md) 给出，本文只讲做法。所有数字来自仓库内 `artifacts/` 的聚合产物，所有代码片段摘自 `src/spam_classifier/` 的实际实现。

## 0. 全局思路

这个项目表面上是一个文本分类任务，实际的难点有三个：

1. **中文邮件几乎全是脏数据**——64,620 封里编码声明不可信、MIME 结构残缺、HTML 混正文。不先解决"能不能读出正确文本"，后面所有模型指标都没有意义。
2. **机器学习项目最容易自欺**——只要步骤顺序稍微乱一点，测试集信息就会通过调参、选特征、反复看指标的方式漏进模型，报告出一个好看但不可复现的数字。
3. **语料本身类别极不平衡**——原始 spam 占 66.32%，但去重后降到 37.00%。只看准确率会严重误导。

所以整个项目的骨架是这样一条链：

```
读原始邮件 → 得到可信文本 → 定义"相同" → 整组不跨集合划分
  → 只在训练集学词表 → 验证集选参 → 清洗对照 → 锁定后才碰测试集
```

**链上每一环都在写入"来源指纹"，下一环加载时逐一校验，对不上就拒绝运行。** 这是本项目与"跑通就行"的最大区别：不是防止结果出错，而是防止**用旧产物配新代码**得出看似合理的新结论。

## 1. 第 1 步：只读索引，不碰邮件

### 要解决的问题

拿到 64,620 封邮件，第一件事是"搞清楚有什么"。但直接开始解析，会立刻陷入几十万次解码失败里，且无法判断失败是数据的问题还是代码的问题。

### 怎么做的

**只读 `full/index` 这一个文件，不打开任何一封邮件。** [index_audit.py](file:///c:/Users/17317/Desktop/solo/Python-teamwork/src/spam_classifier/index_audit.py) 做四件事：

**① 用路径生成稳定 ID，而不是内容哈希**

```python
def mail_id(relative_path: str) -> str:
    """An ID for a path, not a content hash or a deduplication signature."""
    value = ("trec06c-path-v1\0" + relative_path).encode("utf-8")
    return "trec06c_" + hashlib.sha256(value).hexdigest()
```

为什么不用内容哈希？因为后面去重要靠内容哈希判定"这封和那封是同一封"。如果 ID 也是内容哈希，两封内容相同的邮件会拿到同一个 ID，账本就对不上了。**ID 必须是"这是哪个文件"的标识，不是"这是什么内容"的标识**——两个概念必须分开。

注意 `trec06c-path-v1\0` 这个前缀和 `\0` 分隔符：加了版本号，将来换 ID 生成规则时，老账本能被识别为"旧规则产物"而不是被误当成数据损坏。

**② 过滤 macOS 压缩包残留**

```python
def is_auxiliary(relative_path: str) -> bool:
    return any(
        part == "__MACOSX" or part == ".DS_Store" or part.startswith("._")
        for part in PurePosixPath(relative_path).parts
    )
```

课程给的 zip 在 macOS 上打包过，解压后带 `__MACOSX/` 和 `._` 前缀的伴生文件。这些不是邮件，若混进去会被当成解析失败样本，污染所有统计。

**③ 抽样要可复现且类别均衡**

```python
def balanced_sample(records: list[dict], size: int, seed: int) -> list[dict]:
    groups = {
        label: sorted(
            (row for row in records if row["status"] == "eligible" and row["label_name"] == label),
            key=lambda row: row["relative_path"],
        )
        for label in sorted(LABELS)
    }
    target = min(size, sum(map(len, groups.values())))
    quotas = {label: min(len(rows), target // 2) for label, rows in groups.items()}
    while sum(quotas.values()) < target:
        for label, rows in groups.items():
            if quotas[label] < len(rows) and sum(quotas.values()) < target:
                quotas[label] += 1
    rng = random.Random(seed)
```

三个设计点：先按 `relative_path` 排序再抽样，**保证输入顺序不影响结果**；ham/spam 各占一半，**保证开发样本能同时暴露两类问题**；用 `random.Random(seed)` 局部实例而非全局 `random`，**避免污染其他模块的随机状态**。

抽出的 400 封（ham 200 + spam 200）只用于调试解析器，**不进任何正式统计**。

**④ 分位数用最近秩法并写进方法名**

```python
result["percentile_method"] = "nearest_rank_ceil_p_times_n"
result[name + "_bytes"] = ordered[max(0, math.ceil(probability * len(ordered)) - 1)]
```

不同库的分位数插值方式不同，同一份数据能算出三个值。**把方法名写进输出**，别人才知道这个数是怎么来的。`math.ceil(p*n)` 是最近秩法，p95 就是第 95% 位置的那个观测值，不插值。

**结果**：主索引 64,620 封（ham 21,766 / spam 42,854），零异常。

## 2. 第 2 步：把邮件读成可信的文本

这是整个项目代码量最大、最难的部分（347 行）。核心难点不是"解析邮件"，而是**判断什么时候该放弃一封邮件**。

### 2.1 MIME 结构选择：宁缺毋滥

一封 `multipart/alternative` 邮件同时含纯文本和 HTML 两个版本。两个都收会导致同一内容被计两次，纯文本和 HTML 版本不一致时又会引入矛盾。

```python
if part.get_content_subtype() == "alternative":
    # Examine plain parts first; only decode fallback HTML if needed.
    ordered = sorted(children, key=lambda child: child.get_content_type() != "text/plain")
    for child in ordered:
        decoded_text, cleaned, selection, has_html = extract(child, depth + 1)
        if _usable_text(cleaned):
            return decoded_text, cleaned, selection, has_html
    return "", "", "none", False
```

**先试纯文本，纯文本不可用才退到 HTML。** 这不是偏好问题：纯文本是发送方声明的正文，HTML 是富文本渲染版，两者冲突时 HTML 往往是模板套壳后的产物。

关键是这个 `return` 在**第一个可用子部分**就返回了，不是遍历完再挑——`alternative` 的语义就是"这些是同一内容的不同表示，任选其一即可"。

另外两种 MIME 类型各有专门处理：

```python
if part.get_content_subtype() == "related":
    start = part.get_param("start", header="content-type")
    root = children[0]
    if start:
        matching = [child for child in children if str(child.get("Content-ID", "")).strip() == str(start).strip()]
        if matching:
            root = matching[0]
        else:
            actions.append("related_start_not_found")
    return extract(root, depth + 1)
```

`related` 是"正文 + 内嵌图片"，`start` 参数指明哪个子部分是真正正文。找不到就记 `related_start_not_found` 而不是随便挑一个——**记录降级事实，比假装没发生要好**。

`message/rfc822`（转发的整封子邮件）和带附件的 part 全部跳过，**只计 `skipped_forwarded` / `skipped_attachments` 数量**。

还有深度保护：

```python
if depth > 20:
    actions.append("mime_depth_limit")
    return "", "", "none", False
```

恶意或损坏邮件可能有超深嵌套，不设上限会栈溢出。

### 2.2 编码恢复：候选顺序 + 严格解码 + 合理性检验

**候选顺序**（这是整套编码恢复的骨架）：

```python
candidates.extend(hint_codecs + ["utf-8", "gb18030", "gbk"])
candidates = list(dict.fromkeys(candidates))
```

`hint_codecs` 按优先级是：BOM → HTML meta charset → （无声明时）ASCII 快速路径。然后是三个中文编码兜底。

用 `gb18030` 而不是 `gbk`：`gb18030` 是 GBK 的超集，能多解一些生僻字。`dict.fromkeys` 去重且**保持顺序**——顺序决定优先级，不能用集合。

**为什么用 `errors="strict"` 而不是 `errors="replace"`**：

```python
for charset in candidates:
    try:
        text = data.decode(charset, errors="strict")
        # A permissive codec can decode binary/control bytes successfully.
        if _control_count(text) / max(1, len(text)) > CONTROL_LIMIT:
            continue
```

这是本项目最关键的编码细节。**ISO-8859-1 能"成功"解码任意字节序列**——它是单字节映射，永不报错。所以 `errors="replace"` 的策略会静默地把二进制解码成乱码文本，看起来"成功"了。

用 `strict` 时，错误的编码会抛异常，继续试下一个候选。但即使 `strict` 成功，仍要做合理性检查——**某些编码确实能严格解出二进制内容**。所以加了控制字符比例检查：

```python
def _control_count(text: str) -> int:
    return sum(unicodedata.category(char) in {"Cc", "Cs"} and char not in "\n\r\t" for char in text)
```

控制字符占比超 2% 判定为二进制，继续换候选。

**识别"声明错误"**是另一个精妙之处：

```python
if charset == declared_codec:
    alternatives = list(hint_codecs)
    if charset in {"iso8859-1", "cp1252"}:
        alternatives.extend(["utf-8", "gb18030"])
    for other in dict.fromkeys(alternatives):
        if other == charset:
            continue
        try:
            alternative = data.decode(other, errors="strict")
        except (UnicodeError, LookupError):
            continue
        cjk = _cjk_count(alternative)
        if (_control_count(alternative) == 0 and _cjk_count(text) == 0
                and cjk >= 4 and cjk / max(1, len(alternative)) >= 0.15):
            return Decoded(alternative, declared, other, True, "suspected_misdeclared_charset")
```

场景：邮件声明 `iso8859-1`（很多老邮件这么写），实际是 UTF-8 或 GBK。声明的编码能"成功"解码，但解出来没有汉字——**"能解码"不等于"解对了"**。

所以当声明编码解出 0 个汉字时，用备选编码再试一次：若备选能严格解码、控制字符为 0、汉字数 ≥ 4 且占比 ≥ 15%，就采用备选并打上 `suspected_misdeclared_charset` 警告。

**这四个条件缺一不可**：
- `control_count == 0`：排除二进制
- `_cjk_count(text) == 0`：声明编码本身没出汉字，才说明声明可疑
- `cjk >= 4`：至少要有一定量汉字才谈得上"这是中文邮件"
- `cjk / len >= 0.15`：占比太低说明只是混了几个汉字的英文邮件

全部候选都失败时，用 `errors="replace"` 兜底，但**按惩罚分选最优**：

```python
choices = []
for charset in candidates:
    try:
        text = data.decode(charset, errors="replace")
        penalty = text.count("\ufffd") + _control_count(text)
        choices.append((penalty, len(choices), text, charset))
    except (UnicodeError, LookupError):
        pass
if not choices:
    return Decoded(data.decode("utf-8", errors="replace"), declared, "utf-8", True)
_, _, text, charset = min(choices)
```

惩罚 = 替换符数量 + 控制字符数量。`len(choices)` 作为第二排序键保证**同分时按候选顺序取先者**，结果确定。

### 2.3 base64 陷阱：不能信任标准库的宽松解码

```python
if token == "base64":
    # Populate standard-library transfer defects, but do not trust its
    # permissive decoder to turn already-decoded prose into random bytes.
    part.get_payload(decode=True)
    compact = re.sub(rb"\s+", b"", raw_value)
    try:
        return base64.b64decode(compact + b"=" * ((-len(compact)) % 4), validate=True)
    except Exception:
        candidate = _decode_bytes(raw_value, part.get_content_charset())
        text = candidate.text
        visibly_text = (_cjk_count(text) >= 2 or HTML_TAG.search(text) is not None
                        or len(re.findall(r"[A-Za-z]{2,}[ \t]+[A-Za-z]{2,}", text)) >= 2)
        if visibly_text and "\ufffd" not in text and _control_count(text) == 0:
            actions.append("mislabeled_base64_text_fallback")
            return raw_value
        raise ValueError("Invalid base64 without a safe plain-text fallback.")
```

这段处理了一个真实存在的坑：**有些邮件声明 base64，但内容其实已经是明文**。标准库的 `get_payload(decode=True)` 会把这堆明文当 base64 解，解出一堆随机字节，而且**不报错**。

所以这里用 `validate=True` 严格解 base64。失败后不直接放弃，而是检查"这其实是不是明文"：有 ≥2 个汉字、或含 HTML 标签、或有 ≥2 个英文单词（词间有空格）——满足其一且无替换符、无控制字符，就判定为"标错了 base64 的明文"，直接用原文并记 `mislabeled_base64_text_fallback`。

`visibly_text` 用"汉字数 / HTML 标签 / 英文单词"三条独立判据，是因为不同语种的垃圾邮件形态不同——纯中文、HTML 模板、纯英文促销各命中一条。

### 2.4 判断"这坨东西不是正文"

```python
replacement_ratio = text.count("\ufffd") / max(1, len(text))
binary_like = _control_count(text) / max(1, len(text)) > CONTROL_LIMIT
boundary = part.get_boundary()
exact_boundary = bool(boundary and re.search(
    r"(?m)^--" + re.escape(boundary) + r"(?:--)?[ \t]*$", text.replace("\r\n", "\n")
))
framed = broken_multipart and (exact_boundary or MIME_HEADER_BLOCK.search(text) is not None)
if replacement_ratio > REPLACEMENT_LIMIT or binary_like or _encoded_blob(text) or framed:
    actions.append("body_candidate_rejected")
    rejected_body = True
    return text, "", "rejected", False
```

四道关卡，任一命中就拒收该正文：

| 检查 | 判据 | 拦的是什么 |
|---|---|---|
| `replacement_ratio` | > 2% | 解码失败的垃圾字节 |
| `binary_like` | 控制字符 > 2% | 二进制附件 |
| `_encoded_blob` | 连续 160+ 字符无空格且是 base64 字符集 | 忘了解码的编码块 |
| `framed` | 文本里出现 MIME 边界或头部块 | 结构损坏导致头体没分开 |

`_encoded_blob` 特意用"无空格"作判据：

```python
def _encoded_blob(text: str) -> bool:
    # Spaces between prose words distinguish it from a wrapped encoded block.
    if re.search(r"[ \t]", text.strip()):
        return False
    compact = re.sub(r"\s+", "", text)
    return len(compact) >= 160 and re.fullmatch(r"[A-Za-z0-9+/]+={0,2}", compact) is not None
```

正常散文有空格，base64 块没有。**这一条能拦住"双重编码"——已经解码过一次但其实是嵌套 base64 的邮件。**

拒收时返回 `rejected` 状态并置 `rejected_body = True`，**这会影响最终状态判定**（见 2.6）。

### 2.5 清洗：保留语义，抹掉身份

```python
def clean_text(text: str) -> str:
    """Normalize Unicode and obvious contact identifiers without dropping digits."""
    text = unicodedata.normalize("NFKC", text).lower()
    text = text.replace("\r\n", "\n").replace("\r", "\n")
    text = "".join(
        char for char in text
        if char in "\n\t" or unicodedata.category(char) not in {"Cc", "Cf", "Cs"}
    )
    text = "\n".join(re.sub(r"[^\S\n]+", " ", line).strip() for line in text.split("\n"))
    text = URL.sub(" urltoken ", text)
    text = EMAIL.sub(" emailtoken ", text)
    text = PHONE.sub(" phonetoken ", text)
    text = "\n".join(re.sub(r"[^\S\n]+", " ", line).strip() for line in text.split("\n"))
    return re.sub(r"\n{3,}", "\n\n", text).strip()
```

逐步拆解：

1. **NFKC 规范化**：全角转半角、兼容字符统一。这一步同时把大量"伪乱码"还原成正常文字。
2. **转小写**：中文无影响，英文统一。
3. **删控制字符**：`unicodedata.category(char)` 属于 `Cc`（控制）、`Cf`（格式）、`Cs`（代理）的一律删，但**保留 `\n\t`**——换行和缩进承载段落结构。
4. **逐行规整**：行内连续空白压成单空格，去首尾空格。**保留换行**。
5. **身份信息掩码**：URL → `urltoken`，邮箱 → `emailtoken`，电话 → `phonetoken`。

**为什么用占位符而不是直接删除**？直接删会让"请联系 138..."和"请联系"变成同一个句子，引入虚假重复。用固定占位符既移除了身份信息，又保留了"这里原本有个联系方式"这个结构信号。

电话正则写得最复杂，因为要避免误伤普通数字：

```python
PHONE = re.compile(
    r"(?<!\d)(?:\+?86[- ]?)?(?:1[3-9]\d{9}|0\d{2,3}[- ]?\d{7,8})(?!\d)"
    r"|(?<!\d)(?:\+\d{1,3}[- .]?)?\(?\d{2,4}\)?[- .]\d{3,4}[- .]\d{4}(?\!\d)"
    r"|(?<!\d)\+\d{8,15}(?!\d)"
)
```

`(?<!\d)` 和 `(?!\d)` 是前后向断言，保证不匹配长数字串的中段。`1[3-9]` 限定手机号第二位。**保留数字本身**（注释里写明 "without dropping digits"）——因为"第 3 号楼"这类信息不该丢。

6. **合并多余空行**：`\n{3,}` → `\n\n`，最多两个连续换行。

**`text_clean` 与 `text_unstripped_html` 的区别**——这是为第 7 步对照实验预留的：

```python
result["text_clean"] = "\n".join(value for value in (result["subject_clean"], body_clean) if value).strip()
result["text_unstripped_html"] = "\n".join(
    value for value in (result["subject_clean"], clean_text(body_decoded) if body_clean else "") if value
).strip()
```

前者用**去标签后的可读文本**（`body_clean`，经过 `html_to_text`），后者用**保留 HTML 标签的原始正文**（`body_decoded`）。两者唯一区别就是标签在不在。**第 7 步只改这一个变量，就能干净地测出"去 HTML 标签到底有没有用"。**

### 2.6 状态判定：把"降级"和"失败"分开

```python
if not result["usable"]:
    result["parse_status"] = "quarantined" if rejected_body or "subject_candidate_rejected" in actions else "empty"
elif result["body_empty"]:
    result["parse_status"] = "subject_only"
elif result["mime_defects"] or actions or result["decode_fallback"] or result["replacement_characters"] or result["encoding_warnings"]:
    result["parse_status"] = "recovered"
else:
    result["parse_status"] = "ok"
```

四个状态，语义严格区分：

| 状态 | 含义 | 数量 |
|---|---|---|
| `ok` | 一切正常 | 29,891 |
| `recovered` | 有回退、缺陷或警告，但拿到了可用文本 | 33,307 |
| `subject_only` | 只有主题可用，正文空 | 1,422 |
| 隔离/错误 | 拿不到可用文本 | **0** |

`recovered` 的判定条件是"有任一异常但仍然可用"——**它不是失败，是"成功但带伤"**。把这个状态单独拿出来，是因为它占了一半多的数据，如果混进 `ok`，就无法回答"我们的解析器在什么情况下会退化"。

隔离为 0 值得强调：这不是"没发现问题"，而是**每一封都拿到了可用文本**。

## 3. 第 3 步：定义"相同"，并让相似邮件不跨集合

### 3.1 四种签名

```python
SIGNATURE_FIELDS = ("raw_sha256", "text_sha256", "body_sha256", "ablation_sha256")

def signature(text: str, field: str) -> str:
    return hashlib.sha256(("trec06c-content-v1\0" + field + "\0" + text).encode("utf-8")).hexdigest()
```

| 签名 | 算在什么上 | 用来发现什么 |
|---|---|---|
| `raw_sha256` | 原始邮件字节 | 完全相同的邮件 |
| `text_sha256` | 最终 `text_clean` | 规范化后相同的邮件 |
| `body_sha256` | 有效正文 | 正文相同但主题不同 |
| `ablation_sha256` | 保留 HTML 的正文 | 只在 HTML 臂下才相同 |

每个字段**带域分隔前缀**（`field` 参与哈希），所以"内容 A 的 raw"和"内容 A 的 text"哈希值完全不同，不会跨字段碰撞。

### 3.2 为什么需要"分组"，而不只是去重

朴素做法是：把完全相同的邮件去重，然后随机划分。**问题在于"近似重复"**——同一封群发邮件改了个签名档、换了日期、动了一个字，精确哈希不同，但语义上几乎一样。随机划分会让它同时出现在训练集和测试集，模型等于在测试时见过答案。

所以本项目用**并查集**把所有"共享任一签名"的邮件连成组，**整组分配到同一个集合**：

```python
parent = {row["mail_id"]: row["mail_id"] for row in metadata}

def find(value):
    while parent[value] != value:
        parent[value] = parent[parent[value]]  # 路径压缩
        value = parent[value]
    return value

def union(first, second):
    a, b = sorted((find(first), find(second)))
    parent[b] = a

buckets = {field: defaultdict(list) for field in SIGNATURE_FIELDS}
for row in metadata:
    for field in SIGNATURE_FIELDS:
        if row[field]:
            buckets[field][row[field]].append(row)
for groups in buckets.values():
    for group in groups.values():
        for row in group[1:]:
            union(group[0]["mail_id"], row["mail_id"])
```

**路径压缩**让查找接近常数时间。`union` 里排序保证 `a < b`，所以合并方向确定——**并查集的结果与遍历顺序无关**，否则同一份数据两次运行可能得到不同的组划分。

关键在于**传递性**：A 和 B 共享正文，B 和 C 共享原始字节，那么 A、B、C 必须在同一组，哪怕 A 和 C 之间没有任何直接匹配。并查集天然处理这个传递闭包。

结果：30,817 个组，最大组 1,409 封，p50=1，p95=5，p99=21。**最大组 1,409 封**说明存在大规模群发，正是需要整组隔离的对象。

先处理三类"不能当代表"的情况：

```python
conflicts = defaultdict(set)
```

本批语料 `mixed_label_groups: 0`，即没有冲突。但代码必须处理这个情况，因为处理逻辑本身是正确性的一部分。

### 3.5 整组贪心分配

```python
def assign_splits(representatives: list[dict], *, seed: int, ratios: dict) -> list[dict]:
    """Greedy whole-group allocation minimizing normalized class count error."""
    validate_parameters(seed, ratios)
    groups = defaultdict(list)
    for row in representatives:
        groups[row["leakage_group_id"]].append(row)
    totals = Counter(row["label_name"] for row in representatives)
    targets = {label: integer_targets(totals[label], ratios) for label in LABELS}
    counts = {name: Counter() for name in SPLITS}
    assignments = {}
    for group_id, group in groups.items():
        if any(row["forced_train"] for row in group):
            assignments[group_id] = "train"
            counts["train"].update(row["label_name"] for row in group)
    remaining = sorted((group_id for group_id in groups if group_id not in assignments),
                       key=lambda key: (-len(groups[key]), signature(f"{seed}\0{key}", "split-order")))
    for group_id in remaining:
        group_counts = Counter(row["label_name"] for row in groups[group_id])

        def cost(name):
            # Other sets' terms stay constant; compare only this set's delta.
            delta = sum(((counts[name][label] + group_counts[label] - targets[label][name]) ** 2
                         - (counts[name][label] - targets[label][name]) ** 2)
                        / max(1, targets[label][name]) for label in LABELS)
            return delta, signature(f"{seed}\0{group_id}\0{name}", "split-tie")

        chosen = min(SPLITS, key=cost)
        assignments[group_id] = chosen
        counts[chosen].update(group_counts)
```

四个关键设计：

**① 目标数用整数分配，避免小数累积**

```python
def integer_targets(total: int, ratios: dict) -> dict[str, int]:
    exact = {name: total * ratios[name] for name in SPLITS}
    result = {name: math.floor(exact[name]) for name in SPLITS}
    order = sorted(SPLITS, key=lambda name: (-(exact[name] - result[name]), SPLITS.index(name)))
    for name in order[:total - sum(result.values())]:
        result[name] += 1
```

先取下整，把余数按小数部分从大到小补上去。**`SPLITS.index(name)` 是稳定的第二排序键**，保证余数相同时按 train→validation→test 的固定顺序，不依赖字典顺序。

**② 成本函数只算增量**

```python
delta = sum(((counts[name][label] + group_counts[label] - targets[label][name]) ** 2
             - (counts[name][label] - targets[label][name]) ** 2)
            / max(1, targets[label][name]) for label in LABELS)
```

目标是让各集合的**归一化类别计数误差平方和**最小。注释里写 "Other sets' terms stay constant; compare only this set's delta"——因为分母 `targets[label][name]` 对三个集合是常数，比较时只剩增量项，**把 O(3) 的计算降成一次求值**。

归一化（除以目标数）是必须的：不归一的话 spam 集合的计数误差会压过 ham 的，因为 spam 数量是 ham 的近两倍。

**③ 先大后小**

```python
remaining = sorted(..., key=lambda key: (-len(groups[key]), signature(f"{seed}\0{key}", "split-order")))
```

大组先分配。**大组最难安置**——小组合并就能填平误差，大组一放进去就可能超差。排序用 `signature(f"{seed}\0{key}", ...)` 而不是 `key` 本身，保证**在长度相同时的顺序由种子决定且完全确定**。

**④ 并列时用签名打破平局**

```python
return delta, signature(f"{seed}\0{group_id}\0{name}", "split-tie")
```

代价函数的第二个返回值是**确定性 tie-break**。`min` 按元组比较，第一项相同就比第二项。这保证**同一个种子永远得到同一个划分**，而不是"取决于字典遍历顺序"。

**为什么不用随机划分？** 因为随机划分无法保证"整组不跨集合"——随机是逐封的。要整组分配，就得用确定性优化代替随机采样。种子仍保留，用于打破平局和确保可复现。

**结果**：训练 23,792（ham 14,988 / spam 8,804）、验证 5,099（3,212 / 1,887）、测试 5,097（3,211 / 1,886）。

## 4. 第 4 步：特征工程——只把词表学在训练集

### 4.1 分词规则

```python
TOKEN_PATTERN = re.compile(r"[a-z0-9\u3400-\u9fff]+\Z")
TOKENIZER = jieba.Tokenizer()
jieba.setLogLevel(logging.ERROR)

def tokenize_text(text: str) -> list[str]:
    text = unicodedata.normalize("NFKC", text).lower()
    tokens = []
    for value in TOKENIZER.cut(text, cut_all=False, HMM=False):
        token = value.strip()
        if token in PLACEHOLDERS:
            tokens.append(token)
        elif (token not in STOPWORDS and TOKEN_PATTERN.fullmatch(token)
              and len(token) <= 40 and not (len(token) == 1 and token.isascii() and token.isalpha())):
            tokens.append(token)
    return tokens
```

| 规则 | 理由 |
|---|---|
| `cut_all=False` | 精确模式，不用全切 |
| `HMM=False` | **关闭新词发现**。HMM 会根据语料猜词，结果随语料变化，不可复现 |
| `TOKEN_PATTERN` | 只保留小写字母、数字、CJK，排除标点 |
| `len <= 40` | 排除超长乱码串 |
| 单个 ASCII 字母丢弃 | 英文单字母（a、i）几乎无判别力，还可能来自乱码 |
| 占位符豁免 | `urltoken` 等要保留，它们是结构信号 |

**`HMM=False` 是可复现性的关键**。开启 HMM 后，词表依赖语料统计，同样的代码在不同的训练子集上会切出不同的词，导致"同一份数据跑两次结果不同"。

停用词表 57 项，公开词表 53 项，都放在 `config/` 并被 SHA256 指纹锁定。

### 4.2 TF-IDF

```python
def make_feature_pipeline() -> Pipeline:
    return Pipeline([("tfidf", TfidfVectorizer(
        tokenizer=tokenize_text, token_pattern=None, lowercase=False,
        ngram_range=(1, 1), min_df=2, max_df=1.0, max_features=50000,
        sublinear_tf=True, use_idf=True, smooth_idf=True, norm="l2", dtype=np.float64,
    ))])
```

| 参数 | 值 | 理由 |
|---|---|---|
| `min_df=2` | 2 | 只出现 1 次的词无法学到权重，去掉 |
| `max_features=50000` | 5 万 | 内存与效果的折中 |
| `sublinear_tf=True` | 开 | 次线性词频。1 次和 10 次出现，权重差 10 倍不合理 |
| `smooth_idf=True` | 开 | 平滑 IDF，避免高频词 IDF 为 0 |
| `norm="l2"` | L2 | 归一化，让长邮件不会因为词多而天然占优 |
| `dtype=float64` | 双精度 | 跨平台一致性 |
| `ngram_range=(1,1)` | 一元 | 保持特征可解释——二元组无法在公开词表里讨论 |
| `lowercase=False` | 关 | 已在分词器里小写化，避免重复处理 |

**最关键的一条不在参数里，在用法上**：

```python
# 验证/测试只调用 .transform()，绝不调用 .fit()
```

TF-IDF 必须在**训练集上**学词表和 IDF。如果在验证/测试上 fit，测试集的词频分布会渗入 IDF，等于用测试集信息训练模型。

代码层面靠两条保障：

**① 变换前后指纹不变**

```python
before = fitted_feature_state(vectorizer)
predicted = pipeline.predict(validation)
if fitted_feature_state(vectorizer) != before:
    raise ValueError("Validation transform changed the fitted vocabulary/IDF.")
```

`fitted_feature_state` 记录词表哈希和 IDF 哈希：

```python
def fitted_feature_state(vectorizer) -> dict:
    vocabulary = sorted((term, int(index)) for term, index in vectorizer.vocabulary_.items())
    return {
        "vocabulary_sha256": hashlib.sha256(json.dumps(vocabulary, ensure_ascii=False, separators=(",", ":")).encode("utf-8")).hexdigest(),
        "idf_sha256": hashlib.sha256(np.asarray(vectorizer.idf_, dtype="<f8").tobytes()).hexdigest(),
    }
```

**变换后如果词表或 IDF 变了，直接抛异常。** 这把"不能 fit 测试集"从纪律变成了代码约束。

**② 加载时强制 `fit_scope == "train_only"`**

```python
if (feature_sha != summary["feature_source_sha256"] or ... or summary["fit_scope"] != "train_only"):
    raise ValueError("Feature rules, validation or runtime changed; rerun feature verification.")
```

**结果**：50,000 维，训练矩阵非零元素 3,664,021。

### 5.3 指标计算

```python
def validation_metrics(y_true, y_pred) -> dict[str, Any]:
    tn = int(np.count_nonzero((truth == 0) & (prediction == 0)))
    fp = int(np.count_nonzero((truth == 0) & (prediction == 1)))
    fn = int(np.count_nonzero((truth == 1) & (prediction == 0)))
    tp = int(np.count_nonzero((truth == 1) & (prediction == 1)))
    ...
    return {
        "confusion_matrix": {"tn": tn, "fp": fp, "fn": fn, "tp": tp},
        "accuracy": accuracy,
        "spam_precision": ratio(tp, tp + fp),
        "spam_recall": ratio(tp, tp + fn),
        "ham_f1": ratio(2 * ham_precision * ham_recall, ham_precision + ham_recall),
        "spam_f1": ratio(2 * spam_precision * spam_recall, spam_precision + spam_recall),
        "macro_f1": float((ham_f1 + spam_f1) / 2.0),
        "ham_false_positive_rate": ratio(fp, fp + tn),
    }
}
```

`_binary_vector` 还做了严格输入校验：


**所以报告里写的是**："去标签 macro-F1 高 0.0213 个百分点……实际改变输入的训练/验证样本仅 156/36 封，净少漏报 1 封，**不能宣称普遍或显著提升**"。

锁定去标签**不是**因为它更好，而是因为**预设的排序规则**在两种表示上都指向它，且它让最终流程的语义更清晰（模型看到的是可读文本，不是模板残渣）。这个理由被如实写在文档里。

**这个实验的价值恰恰在于它什么都没证明。** 一个"去 HTML 标签显著提升 2 个百分点"的结论，在只有 156 封样本变化的对照实验里是不可能成立的。

### 7.1 锁的内容

第 7 步结束后，生成 `artifacts/metrics/final_lock.json`，内容是：

锁里固定了：选定的表示、模型名单 `["majority", "nb", "lr"]`、参数 `{"nb": {"alpha": 0.1}, "lr": {"C": 2.0}}`、决策规则 `"estimator.predict; no threshold tuning; no train+validation refit"`、运行时版本、相关源文件哈希、上下游产物哈希。

**最后一条 `decision_rule` 特别重要**，它把几条"不许做的事"写进了机器可校验的契约：
- 不调分类阈值
- 不用训练+验证重新拟合
- 直接用 `predict()`

## 8. 贯穿全程的三条工程主线

上面按数据流讲了 8 个步骤。下面把三条**横切**的工程主线单独拎出来——它们才是这个项目与"能跑就行"的主要区别。

### 8.1 指纹链：每一环都要证明"我还是我"

`dataset.py` 的加载函数是一整段连续的校验：

```python
def load_dataset(root: Path) -> DatasetBundle:
    root = Path(root).resolve()
    art = root / "artifacts"
    cleaning = json.loads((art / "audit/cleaning_summary.json").read_text(encoding="utf-8"))
    frozen = json.loads((art / "audit/split_summary.json").read_text(encoding="utf-8"))
    validation = json.loads((art / "audit/split_validation.json").read_text(encoding="utf-8"))
    if not all(item["passed"] for item in (cleaning, frozen, validation)) or not all(validation["checks"].values()):
        raise ValueError("Resolve cleaning and frozen-split verification first.")
    if frozen["random_state"] != 42 or frozen["target_ratios"] != {"train": .7, "validation": .15, "test": .15}:
        raise ValueError("Unexpected frozen split contract.")
    policy_sha = source_sha256(root, ("src/spam_classifier/data_split.py", "scripts/split_data.py"))
    parser_sha = hashlib.sha256((root / "src/spam_classifier/email_parser.py").read_bytes().replace(b"\r\n", b"\n")).hexdigest()
    checker_sha = hashlib.sha256((root / "scripts/check_splits.py").read_bytes().replace(b"\r\n", b"\n")).hexdigest()
    source = frozen["input_provenance"]
    if (policy_sha != frozen["split_policy_source_sha256"] or policy_sha != validation["split_policy_source_sha256"]
            or parser_sha != cleaning["parser_source_sha256"] or parser_sha != source["parser_source_sha256"]
            or checker_sha != validation["validator_source_sha256"]):
        raise ValueError("Upstream source fingerprint no longer matches validated inputs.")
```

逐条看它在校验什么：

| 校验 | 防的是什么 |
|---|---|
| 三个上游报告 `passed` 且所有 checks 为真 | 上游没验收就往下走 |
| `random_state == 42`、比例 70/15/15 | 划分契约被改 |
| **划分策略源码哈希** 三处一致 | 划分代码改了但产物是旧的 |
| **解析器源码哈希** 两处一致 | 解析逻辑改了但清洗缓存是旧的 |
| **核验脚本源码哈希** 一致 | 核验标准被放宽了 |
| 划分 CSV 的 SHA256 | 冻结的划分文件被改动 |

**核心思想**：产物里记录了"我是用哪个版本的代码生成的"。加载时重新计算当前代码的哈希，和产物里记录的比对。**代码改了但产物没重跑 → 拒绝加载**，而不是拿旧产物配新代码得出看似合理的新结论。

`source_sha256` 的实现有个细节：

```python
def source_sha256(root: Path, names: tuple[str, ...]) -> str:
    digest = hashlib.sha256()
    for name in names:
        digest.update(name.encode("utf-8") + b"\0")
        digest.update((root / name).read_bytes().replace(b"\r\n", b"\n"))
        digest.update(b"\0")
    return digest.hexdigest()
```

**`replace(b"\r\n", b"\n")`**——把换行符归一化后再算哈希。这解决了 Windows/Linux 换行差异：同一份代码在 Windows 检出是 CRLF、Linux 是 LF，**不归一化的话哈希永远对不上**。

文件名和内容都参与哈希（用 `\0` 分隔），所以改了文件名也会被发现。

`model_inputs.py` 里的同类校验更严格，把运行时版本也纳入：

```python
feature_versions = {key: value for key, value in runtime_versions().items() if key != "threadpoolctl"}
if (feature_sha != summary["feature_source_sha256"] or ...
        or feature_versions != summary["versions"] or summary["fit_scope"] != "train_only"):
    raise ValueError("Feature rules, validation or runtime changed; rerun feature verification.")
```

`threadpoolctl` 被排除在外，因为它是并发控制工具，版本变化不影响数值结果。

**这条指纹链的完整路径**：

```
email_parser.py ──源码哈希──→ cleaning_summary.json
      ↓                              ↓
  清洗缓存 SHA256 ←──源文件哈希──────┘
      ↓
  split_summary.json ←──划分策略源码哈希── data_split.py
      ↓
  feature_summary.json ←──特征源码哈希── text_features.py + build_features.py
      ↓                      + 运行时版本 + tokenizer 指纹
  model_selection.json ←──模型源码哈希── model_selection.py + model_inputs.py + train_models.py
      ↓
  final_lock.json ←──全部源文件哈希 + 上下游产物哈希 + 运行时版本 + 决策规则
      ↓
  final_evaluation.json
```

任何一环被改动，整条链断在那一环。

### 8.2 生成与核验分离

每个阶段都是"一个生成脚本 + 一个独立核验脚本"配对：

| 阶段 | 生成 | 独立核验 |
|---|---|---|
| 环境 | `check_environment.py` | — |
| 索引 | `audit_index.py` | `tests/test_index_audit.py` |
| 清洗 | `clean_mail.py` | `check_cleaning.py` |
| 划分 | `split_data.py` | `check_splits.py` |
| 特征 | `build_features.py` | `check_features.py` |
| 模型 | `train_models.py` | `check_models.py` |
| 对照 | `compare_cleaning.py` | `check_ablation.py` |
| 最终 | `evaluate_final.py` | `check_final_results.py` |

**核验脚本不复用生成脚本的中间结果，而是重新算。** 例如 `check_models.py` 自己实现了一份指标计算：

```python
from spam_classifier.model_selection import CANDIDATES, SELECTION_POLICY, make_estimator
```

注释明说"without model-selection helpers"——**核验方和被核验方不能共用同一份计算代码**，否则共同的 bug 会被同时掩盖。

核验方还要做**独立重训**：

```python
refit = clone(pipeline).fit(train, y_train)

    np.array_equal(pipeline.predict(validation), predictions[:, col]) and
    np.array_equal(refit.predict(validation), predictions[:, col]))
```

用 `clone` 拿到一个干净的估计器副本，**从原始数据重新训练**，验证结果可复现。同时检查：

```python
checks[name + "_selected_representation"] = (
    fitted_feature_state(pipeline.named_steps["tfidf"]) ==
    fitted_feature_state(comparisons[lock["representation"]].named_steps["tfidf"]))
```

确认锁定模型的词表/IDF 与当时对照实验选中的一致——**防止"锁的是 A，实际跑的是 B"**。

### 8.3 公开与私有的边界

原始邮件、清洗后的正文、完整词表、稀疏矩阵、模型文件、逐封预测——**全部在 Git 忽略的目录里**。

```
artifacts/processed/    # 邮件文本缓存（Git 忽略）
artifacts/models/       # 模型缓存（Git 忽略）
```

公开的只有：
- 聚合统计（`artifacts/audit/`、`artifacts/metrics/`）
- 固定划分元数据（`artifacts/splits/`，只有 4 列：mail_id / label_name / label / split）
- 图（`artifacts/figures/`）
- 脱敏后的错分概述

**为什么正文不公开**：邮件正文是真实个人通信，含姓名、地址、电话、公司。课程要求附录提供仓库链接，仓库是公开的。`clean_text` 里的掩码是必要但不充分的保护——所以正文干脆不进仓库。

**为什么公开去重账本的哈希而不公开正文**：账本（`dedup_ledger.csv`）记录每封邮件的处置结果、签名哈希、所属组，让划分可被独立验证；但它不含任何原文。
